## 為何「位置較像」仍不是同一角色

| 原因類別 | 本輪實際證據／限制 | 應如何處理 |
|---|---|---|
| 2D→3D 幾何重建 | 同畫布疊圖能確認大剪影與五官位置，但無法決定眼瞼曲率、髮束交疊、鼻口體積及風格化誇張；本輪逆投影只約束可見表面，後腦深度是任意粗胚。 | 把投影吻合作為診斷；美術身份要獨立評估，不能用IoU、Mesh封閉或USD成功替代。 |
| 缺乏多視角設計 | B-v02只有一張3/4頭胸像，沒有可靠的正面、側面、背面或中性表情。自動補完的角度只是推定，不是原畫證據。 | B路線需先由角色美術補正／側／背設計並由Owner確認。即使找回1254 master，這些未知資訊仍不會自動出現。 |
| Sculpt／材質／描線／表情不足 | 已有較接近的位置，但宽曲面髮塊仍是硬葉片；眼皮與耳頰簡化；柔光與單色材質缺少原畫描線、髮內高光節奏和自信眼神。 | 停止此程序化曲面方法。B若获選，改由有同風格作品的角色美術主導頭雕、表情與手繪材質；shader服務原畫，不以「加toon」宣稱身份已修好。 |

前兩項是輸入與重建問題；第三項是本次實作的造型與美術判斷不足。不能把三者全部歸因於AI或512解析度。這次只證明目前這條流程不可靠，不能推論所有AI輔助或所有3D流程都無法還原。

## A0 與 Gameplay 的正式順序

| 階段 | 交付及驗收邊界 |
|---|---|
| G0 | 先完成Windows 7×7盜賊教學驗收，不新增圖片整合要求。現況Pending，須Owner確認操作沒有重大阻礙。 |
| G1 | G0通過後，使用既有B角色卡於職業選擇／人物資訊，A Token於棋盤英雄；只做靜態素材接線與尺寸調整，不擴充動畫系統，不修改Domain規則。 |
| G2–G4 | 依既有Gameplay切片完成戰士築壘、法師魔法之手、盜賊換位與本機雙人對戰；不依賴3D角色動畫。本文件不額外核准技能規則變更。 |
| G5 | 真人遊戲性驗證，確認職業技能與對戰值得玩，再評估哪些技能需要局部Sprite動畫或特效。 |
| 後續iOS | SwiftUI版本接入素材後，針對實際iPhone畫面與觸控另行驗收；不是A0、G0或G1的前置Gate。 |

卡片與Token維持各自用途，不將縮小人物卡冒充完成Token。iOS階段仍需檢查正常局面、技能預覽、危險局面，以及7×7／9×9的角色、資源資訊、技能按鈕與觸控操作；这些驗收不能提前阻塞目前Windows玩法開發。未通過真機驗收也不能因Windows試玩正常而宣稱已通過。

Apple的SpriteKit可用texture序列及actions呈現Sprite動畫，官方文件特別提醒影格尺寸和anchor的一致性；這支持A的可行性，但不代表必須現在把整個棋盤改成SpriteKit。[Apple官方Sprite動畫文件](https://developer.apple.com/documentation/spritekit/animating-a-sprite-by-changing-its-texture)

## B0 暫停後保留的未來評估方案（未授權執行）

若G5後Owner另行重啟B0，才選有相近角色風格作品的美術製作者，以B-v02做身份特徵表與正／側／背設計假設。人工建立頭部平面、眼皮和臉頰，先審表情及主髮束節奏，再做手繪色彩、局部高光和描線。第一輪只需單一可轉動頭部與相同視角比較；身份通過前不增加全身或動作。目前不進行此方案。

Blender Studio公開課程包含頭雕、風格化、表情測試、拓撲及材質等步驟，可作流程參考；本次只讀公開概覽，未取得付費課程或宣稱已有專業雕塑能力。[Blender Studio官方課程](https://studio.blender.org/training/stylized-character-workflow/)

3D美術還必須在iOS runtime保有同樣的画风。Blender的Shader to RGB僅支援EEVEE；由此推論，不能把其节点网络当作可直接移植的iOS材质。B须另验证目标渲染器能表达哪些手绘色彩、分阶阴影和描线，不能只验Blender截图。[Blender5.2官方节点支持说明](https://docs.blender.org/manual/en/5.2/render/eevee/limitations/nodes_support.html)
