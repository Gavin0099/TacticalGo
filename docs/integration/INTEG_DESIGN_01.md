## 5. 建議策略（可被 Owner 推翻）

**以 1.0 為起點，1.1 分層嫁接。** 這是降低返工的選擇，**不是唯一合法的架構**；Git 也不要求出貨版本必須成為新主線的祖先。真正要保住的是：

- 可追溯的出貨版本（已有來源雜湊清單）與**可重建**的來源（L0 負責證明）；
- 出貨線獨立修補的能力（審查退件或緊急修正時不必等整合完成）；
- 修補能被移入整合線，而不是在兩條線各改一次。

選 1.0 起步的理由：它的商業與挑戰修改和 1.1 的 UI 修改位在同一組熱檔，由出貨線起步可以避免出貨線與主幹分叉。反方案「以 1.1 為主幹並移植 1.0 商業」同樣可行（商業程式約 5 個 App 檔案加 `TacticalGoAccess`，閘門有單一入口），取捨由 Owner 決定。

Apple 審查與 Git 整合是兩件事：**審查結果不應阻擋整合分支上的工作，只決定何時能合併與發布。**

### D3 要分成兩個問題

| 問題 | 內容 |
|---|---|
| 免費使用者如何體驗？ | 教學、九個挑戰、牧師教學／技能練習／魔物示範：免費且不扣額度。使用牧師、第二技能或魔物的**完整對局**：與原版完整對局共用前 3 場免費與獎勵廣告額度 |
| 永久解鎖包含什麼？ | 既有 NT$60 永久解鎖者**包含本次 1.1 擴充**，不必再購買。此承諾只涵蓋本次已規劃的擴充，**不等於未來所有大型內容永遠免費** |

計費單位是**完整對局**，不是「用了哪個英雄或規則」。Solo 的完整戰鬥按完整對局計，不另建帳本。升級、續玩、重播、恢復購買不重設免費額度，也不重複扣同一場。

### 三個「看起來安全」的前提不能直接採信

1. **核心預設關閉 ≠ App 預設關閉。** `expansionSkills=false` 是規則層預設；1.1 的 UI 層預設新規則且無版別切換。兩個不同層級的預設不能互相擔保（見 D6）。
2. **存檔分開 ≠ 相容性已通過。** `ExpansionMatchRecord` 獨立保存是隔離設計；仍須在 L1 以測試證明：舊存局可讀、缺少新欄位時採原版預設、升級後續玩不改規則、兩種紀錄不混入錯誤的重播或計費流程。
3. **單一 `canStartMatch` 呼叫點 ≠ 所有入口都受控。** 新增的擴充對局、討伐、Solo、重新開始與復原都可能有不同入口。C0 須列舉所有完整對局入口，並以測試證明每一個都經過授權判定。

## 8. 驗收（工程與真人分開）

**工程（自動化）**：Swift 全套測試、兩邊 Golden 與逐步等價、1.0 存檔讀取、帳本邊界、乾淨建置、Release 預檢、UI 測試（iPhone 17／SE／iPad）。

**真人（不可由測試取代，須 Owner 或試玩者）**：

1. 玩家能否在不看說明的情況下理解各職業第二技能做什麼、何時可用（含盜賊「只有一招」的回報）。
2. 牧師是否「好用」：奉獻值得用的局面是否存在（Owner 先前回報不好用）。
3. 包圍魔物時是否有明確回饋（Owner 先前回報沒有反應）。
4. 戰鬥演出是否清楚、有重量感；聲音與動作是否同步。
5. 連續遊玩數局後是否仍想再玩。
