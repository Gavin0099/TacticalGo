# C0｜對局、額度與存檔契約（草案）

> 狀態：**Draft v2。只定義契約與測試規格，不改程式。** 日期：2026-10-15。
> **立場：本次整合保留 1.0 既有的計量語意，不順帶改商業規則。** 若要改成「嚴格最多三場」之類的新額度政策，應另立變更，不併入整合。
> 輸入：1.0／1025 快照 `d13fdfa`、1.1／1112 快照 `8c80ceb`（皆為 GitHub 上可取回的固定 SHA）。

> 與 D3／D4／D6 的關係：這些商業與路線決策仍是「建議待確認」；本文件把它們轉成可測的行為，不替 Owner 定案。

## 1. 為什麼先做 C0

「完整對局」不是已定義好的計費規則。1.0 的帳本只知道「某個 UUID 的對局開始、完成」，並不知道畫面名稱；1.1 完全沒有帳本。
若 UI 先接好再回頭決定扣額度的時機與入口，會在高衝突檔案（`PlayableGameView`、`GameStore`）反覆返工。C0 的目標是**先把語意固定成一張可測的行為表**。

## 2. 1.0 目前實際怎麼計額度（[已證實]，來源 `d13fdfa`）

| 面向 | 行為 | 來源 |
|---|---|---|
| 計量對象 | 只有 `AccessMatchKind.battle` 被計量；`tutorial`、`challenge` 型別存在且為 `notMetered` | `AccessLedger.swift` |
| 準入時機 | 建立新局時：已解鎖 → `unlocked`；否則已完成試玩數 < 3 → `trial`；否則有獎勵額度 → `rewarded`；否則 `accessRequired` | `beginMatch` |
| **試玩額度何時被用掉** | **在對局「完成」時**（`authorization == .trial && completed`），不是開局時 | `completedTrialMatches` |
| **獎勵額度何時被用掉** | **在開局時預留**（綁定 `rewardRequestID`），與是否完成無關 | `beginMatch`／`availableRewards` |
| 解鎖者 | 不入帳（`isUnlocked` 來自當下已驗證的 StoreKit 權益，帳本不快取） | `PlayAccess` |
| 「完成」的定義 | 只有真正的終局結果（`GameStatus` 為 `won` 或 `drawn`）存檔後才呼叫 `completeMatch`；復原與重播不能抹除 | `GameStore.swift:35`、`AccessLedger.swift` |
| 認輸／投降 | **不存在**（1.0 App 內沒有此功能） | 全 App 搜尋 |
| 已準入但未完成的對局 | 額度用完或購買撤銷後仍可續玩 | `beginMatch` 註解與測試 |
| 從未登錄的舊局 | 續玩不計量、完成時不追溯扣款 | `testLegacyUnregisteredCompletionIsNotRetroactivelyChargedOrSaved` |
| 入口閘門 | UI 層 `canStartMatch` 一處＋實際扣帳在 `newMatch(authorize:)`；授權失敗會刪除剛建立的記錄 | `PlayableGameView:1374`、`GameStore.newMatch` |
| 不經帳本的入口 | 教學／練習（`startPractice`）、挑戰、**「建立新版技能續玩副本」**（`createCandidateCopy`，建立新記錄身份卻不呼叫授權） | 呼叫點搜尋 |
| 重新開始 | 選單「重新開始」呼叫 `startMatch(rules:)`，等於**新對局、新 UUID、再走一次準入** | `PlayableGameView:1121` |

### 由上表推出的後果（[推論]，C0 須以測試證實或推翻）

1. **試玩期間放棄不扣額度。** 試玩額度只在終局結算，且沒有認輸；玩到終局前離開（或「重新開始」）不會消耗任何額度。
2. **「重新開始」在試玩期免費、在獎勵額度期每次再扣一次。** 兩種額度的消耗時點不同，行為不對稱。
3. **可以預先登錄多場未完成的對局。** 只要 `completedTrialMatches < 3`，每個新開的局都取得 `trial` 準入；之後即使額度歸零，這些已準入的未完成對局仍可續玩並完成。（是否真能同時保有多個進行中存檔，須用測試確認。）
4. 這些是否為「可接受的設計」或「漏洞」，**由 Owner 在 C0 決定**，不由實作端各入口自行解釋。

> **兩種額度時點不同，不必然是錯誤。** 「讓玩家完成三次試玩體驗」與「看廣告換一場對局使用權」可以是不同的產品承諾。是否統一，是新的產品決策，不是整合的必然要求；C0 要求的只是把時點**說清楚並寫成測試**。

## 3. 1.1 目前實際怎麼開局與存檔（[已證實]，來源 `8c80ceb`）

| 面向 | 行為 |
|---|---|
| 額度 | **完全沒有帳本**；所有入口都不計量（無 `onMatchCompleted`、無 `authorize`） |
| 入口 | 原本的 `newMatch(...)`（無 `authorize` 參數）、`startExpansion(...)`／`resumeExpansion()`、`startPractice`、`startR2` |
| 紀錄型別 | 擴充對局使用獨立的 `ExpansionMatchRecord`（`rules` 識別字串與 `version`；註解寫明「原始 1.0 紀錄刻意不遷移」）；原版沿用 `MatchRecord` |
| 紀錄身份 | **`ExpansionMatchRecord` 沒有 UUID 欄位**；`MatchRecord` 有 `id` |
| 相容性測試（存在） | `testLegacyRecordRejectsPriestAndAllUnknownExpansionActions`、`testSoloMetadataRoundtripLegacyDefaultAndInvalidMetadataReject`、`testSavingCandidateLeavesOriginalDiskBytesUntouchedAndReloadsBoth` 等；皆為單元層，不是「由 1.0 出貨二進位實際產生的存檔」 |

## 5. 計量契約（本次整合的建議定案；仍待 Owner 確認）

| # | 問題 | 本次整合的處理 | 理由 |
|---|---|---|---|
| M1 | 「完成」的定義 | **維持**終局 `won`／`drawn` 存檔；不新增認輸功能 | 新增認輸會改變商業行為 |
| M2 | 試玩額度何時扣 | **維持**終局結算；**不新增步數門檻** | 門檻會引入新問題：算雙方還是玩家？結束回合算不算？復原如何計？門檻前重開是否仍無限免費？它沒有消除取捨，只是把取捨藏進一個數字 |
| M3 | 獎勵額度何時扣 | **維持**開局預留；同一場續玩不再消耗；對外說明與測試寫清楚 | |
| M4 | 同時未完成的對局數 | **不新增**全域「只能一場」，**不在新局建立時自動把舊局判為放棄** | 自動放棄會刪除玩家的棋局，是新的破壞性行為 |
| M5 | 重新開始 | **新棋局、新 UUID、重新準入**（維持現況）；與「續玩同一局」明確區分 | 對局身份不應為了優惠政策而混用；日後若要「一次免費重開」，應明確設計那個權益，而不是沿用同一 UUID |
| M6 | 新版技能副本 | **[已實作選項 (a)，Owner 尚未正式裁決]**：純檢視／分析副本不計量；**可繼續遊玩的新分支**不能因為叫「副本」就繼承免費使用權 | 現況 `createCandidateCopy` 建立新記錄身份卻不經準入；這是「恰好沒接線」，不是設計。選項見下 |
| M7 | 解鎖者 | 維持不入帳 | |
| M8 | 升級與恢復購買 | 維持：不重置免費額度，不重複扣同一場 | |
| M9 | 帳本損毀 | 維持既有保護：存局保留、解鎖者不受影響 | |

**M6 選項（須 Owner 選一）：** (a) 副本延續原局的授權狀態——原局已準入（trial／rewarded），副本視為同一場的延續，不再新增免費額度，也不再扣一次；原局從未登錄，副本同樣不計量。(b) 副本視為新完整對局，走準入。 (a) 保住「一場一次準入」，(b) 會改變 1.0 現行行為。

**試玩中途退出不扣、可預先建立多場試玩局：本次不根治。** 這不是沒有風險，而是不在整合裡同時改掉整套計量政策。若產品要求「嚴格最多三場」，另立明確的額度政策變更：設計「已完成＋已預留」的上限與放棄處理，而不是挑一個步數。

## 5b. 三處語意修正（比再增加條款更重要）

### (1) 「1.0 舊存局」不能一律視為免計量

| 舊局狀態 | 行為 |
|---|---|
| **從未登錄過**（舊 1.0 之前的局、副本、孤兒記錄） | 續玩不追溯計量，完成時也不扣 |
| **已登錄為 `trial`、只是還沒完成** | **完成時仍依原授權結算**（`completedTrialMatches` 照常 +1） |
| **已登錄為 `rewarded`** | 預留早已消耗；續玩不再扣 |

以「帳本中是否已有該 UUID 與其授權」區分，**不能只看它是不是 1.0 的檔案**，否則升級本身就會把原本應結算的試玩局變成免費局。

### (2) 續玩不新增消耗，但可以更新原帳本紀錄

續玩（resume）**不重新準入、不建立第二筆消耗**；但它之後打到終局，或啟動時補做中斷的完成對帳（`reconcileCompletedMatches(ids:)`），**仍可更新原本的帳本紀錄**。因此 E2 的「白名單入口不得寫帳本」過寬，已改寫（見 §7）。

### (3) 「先存記錄、再授權」的中途當機

`newMatch` 先 `records.save(nextRecord)` 再 `authorize(id)`。**[推論]** 若 App 在兩者之間中斷，磁碟上有一筆帳本不認識的新記錄；下次啟動時它與「從未登錄的舊局」無法區分，會被當成可免費續玩的歷史局。C0 須先定義恢復時如何辨識與處理，再讓 L1 實作。選項：

| 選項 | 內容 | 代價 |
|---|---|---|
| R1 | 記錄寫入 `admission: pending`，帳本提交後改為 `registered`；啟動時 pending 者要嘛補登、要嘛刪除 | 需要記錄欄位（與 S4 一起處理） |
| R2 | 先寫帳本「意圖」（intent），再存記錄，最後確認 | 帳本結構要擴充 |
| R3 | 不處理，接受此窗口並寫入已知缺口 | 零成本；但與 E3「不留下半成品」的目標不一致 |

建議 R1，且**不必引進交易框架**。

## 6. 存檔與規則識別契約

| # | 要求 | 驗證方式 |
|---|---|---|
| S1 | 每筆對局記錄保存**規則識別**（原版 `RecordRules` 或擴充 `rules`＋`version`），續玩一律依記錄內的規則，不依 App 目前預設 | 用舊記錄＋改過預設的 App 設定續玩，規則不變 |
| S2 | **只有已知舊 schema 明確允許缺省的欄位，才套用該版本既定預設。** 未知版本或缺少關鍵規則資訊，**不得猜成原版**，應拒絕並保留原檔 | 欄位刪減、未知版本、規則字串缺失三類載入測試；結果須是「拒絕＋原檔不動」，不是靜默降級 |
| S3 | 兩種記錄型別不互相讀取：原版記錄庫拒絕擴充動作；擴充庫不吞下原版記錄 | 已有單元測試；補「同一資料夾兩種檔案並存」的整合測試 |
| **S4** | **`ExpansionMatchRecord` 補持久化的 `id: UUID`**，與帳本以同一識別對映，不另造無 ID 的對映 | 見下 |
| S5 | 升級後 1.0 出貨版寫出的真實資料可被整合版讀取並續玩 | 見下 |
| S6 | 位元組上限與損毀處理沿用現有行為（`byteLimit`、原檔保留） | 沿用既有測試 |

### S4：UUID 代表「這一局」，不是「這一次存檔」

- **生命週期：** 開新局時生成**一次**；自動存檔、續玩、復原**沿用**；重新開始或建立可玩的新分支才生成新 ID。
- **禁止：** 在每次 `ExpansionMatchRecord(session:)` 時順手產生新的 UUID（同一場每存一次就換身份，帳本永遠無法穩定對帳）。
- **舊候選檔缺 ID：** 在受控遷移時**分配一次並保存**，保留原檔；不可每次解碼臨時生成。
- **不可用棋盤或內容雜湊當身份**：兩場獨立對局可能內容完全相同。

### S5：取得真實樣本的路徑（1.0 已有現成入口，不需另做匯出功能）

路徑（已核對 1.0 快照的 `RecordLibraryView`）：**存局與棋譜 → 觀看棋譜 → 準備匯出棋譜 → 分享棋譜 JSON**。取得前先確認手機跑的是 **1.0／1025**，保留版本畫面；各匯出一份**未完成**與一份**已完成**的棋局。

| 樣本 | 能驗證 | 不能驗證 |
|---|---|---|
| 匯出的棋譜 JSON | 真實 App 資料能否被整合版讀取、重播；未完成局能否依原規則續玩 | `recordExport()` 是把記錄**重新編碼**後寫到暫存檔，**不是原始存局檔，也不含額度帳本** |
| 升級前後的原始存局＋帳本狀態 | 原地升級後原授權、已完成數、獎勵預留是否保留，是否重複扣 | 需要在裝置上直接取得原始檔案，**目前沒有取得方式**；列為整合版發布前的驗收缺口 |

樣本尚未取得**不阻擋** C0 定案與隔離的 L1 開發，但必須保留為發布前驗收缺口。

## 7. 入口一致性規格

**機制建議：** 所有「建立完整對局」的路徑必須經過同一個準入函式（例如 `MatchAdmission.begin(kind:rules:id:)`）；UI 的 `canStartMatch` 只負責顯示，不是權限本身。

| 測試 | 內容 |
|---|---|
| E1 | 靜態列出所有會建立 `MatchRecord`／`ExpansionMatchRecord` 的函式；每個都必須呼叫準入，或在**白名單**（教學、挑戰、練習、重播、續玩）內並附理由 |
| E2 | **白名單入口不得新建帳本準入**，也不得因名稱叫 Solo／Expansion 而進白名單。**續玩允許更新原有紀錄**（完成標記、補做對帳），但不得重新準入、不得建立第二筆消耗 |
| E3 | 準入失敗不留下半成品記錄，**每個入口各測一次**。另測**中途當機**：記錄已存 → 尚未準入 → App 中斷 → 下次啟動；此記錄不得被當成免費歷史局（依 §5b-(3) 的選項） |
| E4 | 同一 UUID 重複準入、重複完成、不同 `kind` 重用 UUID 的行為與現有帳本一致 |

## 8. 行為驗收矩陣（期望取自 §5 的建議定案值）

| 情境 | 期望 |
|---|---|
| 新安裝，開原版完整對局並打到終局 | 試玩剩餘 3 → 2 |
| 新安裝，開局後離開不打完 | **不扣**（維持現況；列為已知取捨） |
| 試玩 3 場完成後再開新局 | 要求獎勵或購買 |
| 觀看獎勵後開局 | 消耗 1 個獎勵額度；同一 requestID 不能再用；續玩不再扣 |
| 中途「重新開始」 | **新 UUID、重新準入**（試玩期不扣；獎勵期再預留一次）；不與原局混用身份 |
| 使用牧師完成一場 | 與原版共用同一額度；不另開帳本 |
| 擴充對局完成後重開 App | 帳本與記錄以同一 UUID 對帳一致，不重複扣、不漏扣 |
| 解鎖後 | 完整對局不入帳；撤銷後已準入的未完成局仍可續玩 |
| **從未登錄的舊局**續玩並完成 | 規則不變；不追溯計量 |
| **已登錄為 trial 但未完成的舊局**續玩並完成 | 規則不變；**完成時依原授權結算** |
| 續玩後打到終局 | 更新原有帳本紀錄；不新增第二筆消耗 |
| 記錄已存、準入前當機，重開 App | 依 §5b-(3) 選項處理；**不得靜默視為免費歷史局** |
| 帳本檔損毀 | 解鎖者與既有存局不受影響；顯示可理解的錯誤 |

## 9. 不在 C0 範圍

購買畫面與文案、廣告 SDK 行為、價格與地區、App 隱私申報、介面版面、動畫與語音，以及**任何新的額度政策**（嚴格三場、步數門檻、認輸、自動放棄）。

## 10. C0 的關閉條件

1. Owner 確認 §5 的 M1–M9（可標「照建議」），**特別是 M6 選 (a) 或 (b)**。
2. §5b-(3) 在 R1／R2／R3 中擇一。
3. S4 的 `id: UUID` 與其生命週期被接受；舊候選檔的遷移規則（分配一次並保存）被接受。
4. E1–E4 的規格被接受；允許先寫成「預期失敗」的測試骨架。
5. S5：真實樣本取得方式確定，或明確標為已知缺口。

關閉後才進入 L1。**C0 與 L1 不打包成一個工程。**
