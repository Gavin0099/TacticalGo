# C0｜對局、額度與存檔契約（草案）

> 狀態：**Draft。只定義契約與測試規格，不改程式。** 日期：2026-10-14。
> 輸入：1.0／1025 快照 `d13fdfa`、1.1／1112 快照 `8c80ceb`（皆為 GitHub 上可取回的固定 SHA）。
> 標記：**[已證實]**＝直接讀自上述來源；**[推論]**＝由已證實事實推出，尚待測試證實；**[待決]**＝需 Owner 決定，目前沒有預設答案。
> 與 D3／D4／D6 的關係：這些商業與路線決策仍是「建議待確認」；本文件把它們轉成可測的行為，不替 Owner 定案。

## 1. 為什麼先做 C0

「完整對局」不是已定義好的計費規則。1.0 的帳本只知道「某個 UUID 的對局開始、完成」，並不知道畫面名稱；1.1 完全沒有帳本。
若 UI 先接好再回頭決定扣額度的時機與入口，會在高衝突檔案（`PlayableGameView`、`GameStore`）反覆返工。C0 的目標是**先把語意固定成一張可測的行為表**。

## 2. 1.0 目前實際怎麼計額度（[已證實]，來源 `d13fdfa`）

| 面向 | 行為 | 來源 |
|---|---|---|
| 計量對象 | 只有 `AccessMatchKind.battle` 被計量；`tutorial`、`challenge` 型別存在且為 `notMetered` | `AccessLedger.swift` |
| 準入時機 | 建立新局時：已解鎖 → `unlocked`；否則已完成試玩數 < 3 → `trial`；否則有獎勵額度 → `rewarded`；否則 `accessRequired` | `beginMatch` |
| **試玩額度何時被用掉** | **在對局「完成」時**（`authorization == .trial && completed`），不是開局時 | `completedTrialMatches` |
| **獎勵額度何時被用掉** | **在開局時預留**（綁定 `rewardRequestID`），與是否完成無關 | `beginMatch`／`availableRewards` |
| 解鎖者 | 不入帳（`isUnlocked` 來自當下已驗證的 StoreKit 權益，帳本不快取） | `PlayAccess` |
| 「完成」的定義 | 只有真正的終局結果（`GameStatus` 為 `won` 或 `drawn`）存檔後才呼叫 `completeMatch`；復原與重播不能抹除 | `GameStore.swift:35`、`AccessLedger.swift` |
| 認輸／投降 | **不存在**（1.0 App 內沒有此功能） | 全 App 搜尋 |
| 已準入但未完成的對局 | 額度用完或購買撤銷後仍可續玩 | `beginMatch` 註解與測試 |
| 從未登錄的舊局 | 續玩不計量、完成時不追溯扣款 | `testLegacyUnregisteredCompletionIsNotRetroactivelyChargedOrSaved` |
| 入口閘門 | UI 層 `canStartMatch` 一處＋實際扣帳在 `newMatch(authorize:)`；授權失敗會刪除剛建立的記錄 | `PlayableGameView:1374`、`GameStore.newMatch` |
| 不經帳本的入口 | 教學／練習（`startPractice`）、挑戰、**「建立新版技能續玩副本」**（`createCandidateCopy`，建立新記錄身份卻不呼叫授權） | 呼叫點搜尋 |
| 重新開始 | 選單「重新開始」呼叫 `startMatch(rules:)`，等於**新對局、新 UUID、再走一次準入** | `PlayableGameView:1121` |

### 由上表推出的後果（[推論]，C0 須以測試證實或推翻）

1. **試玩期間放棄不扣額度。** 試玩額度只在終局結算，且沒有認輸；玩到終局前離開（或「重新開始」）不會消耗任何額度。
2. **「重新開始」在試玩期免費、在獎勵額度期每次再扣一次。** 兩種額度的消耗時點不同，行為不對稱。
3. **可以預先登錄多場未完成的對局。** 只要 `completedTrialMatches < 3`，每個新開的局都取得 `trial` 準入；之後即使額度歸零，這些已準入的未完成對局仍可續玩並完成。（是否真能同時保有多個進行中存檔，須用測試確認。）
4. 這些是否為「可接受的設計」或「漏洞」，**由 Owner 在 C0 決定**，不由實作端各入口自行解釋。

## 3. 1.1 目前實際怎麼開局與存檔（[已證實]，來源 `8c80ceb`）

| 面向 | 行為 |
|---|---|
| 額度 | **完全沒有帳本**；所有入口都不計量（無 `onMatchCompleted`、無 `authorize`） |
| 入口 | 原本的 `newMatch(...)`（無 `authorize` 參數）、`startExpansion(...)`／`resumeExpansion()`、`startPractice`、`startR2` |
| 紀錄型別 | 擴充對局使用獨立的 `ExpansionMatchRecord`（`rules` 識別字串與 `version`；註解寫明「原始 1.0 紀錄刻意不遷移」）；原版沿用 `MatchRecord` |
| 紀錄身份 | **`ExpansionMatchRecord` 沒有 UUID 欄位**；`MatchRecord` 有 `id` |
| 相容性測試（存在） | `testLegacyRecordRejectsPriestAndAllUnknownExpansionActions`、`testSoloMetadataRoundtripLegacyDefaultAndInvalidMetadataReject`、`testSavingCandidateLeavesOriginalDiskBytesUntouchedAndReloadsBoth` 等；皆為單元層，不是「由 1.0 出貨二進位實際產生的存檔」 |

**直接後果（[推論]）：** 帳本與紀錄以 UUID 對帳（`reconcileCompletedMatches(ids:)` 讀 `MatchRecord.id`）。擴充對局沒有 UUID，**目前無法被帳本登錄或對帳**。C0 必須決定：給擴充紀錄一個身份欄位，或帳本改用不依賴紀錄 ID 的對映。

## 4. 對局分類（[待決]；右欄為建議，待 Owner 確認）

| 行為／入口 | 是否「完整對局」 | 是否計量 | 備註 |
|---|---|---|---|
| 教學（5 步） | 否 | 否 | 現況已不計量 |
| 九個挑戰 | 否 | 否 | 現況已不計量 |
| 牧師教學、技能練習、魔物示範 | 否 | 否 | 1.1 現況不計量；建議維持免費 |
| 原版規則：雙人完整對局 | 是 | 是 | 現況計量 |
| 原版規則：Solo（對電腦）完整對局 | 是 | 是 | 現況計量；不另建帳本 |
| 擴充規則（牧師／第二技能／魔物）完整對局，雙人或 Solo | 是 | 是 | 建議與原版**共用同一額度**（D3） |
| 續玩（resume） | 否（不是新對局） | 否 | 已準入者保留原準入 |
| 重播／檢視棋譜 | 否 | 否 | |
| 重新開始 | 新對局 | 依 §5 決定 | 目前行為見 §2 推論 2 |
| 建立新版技能續玩副本 | 新身份、延續舊局 | **[待決]** | 目前不計量；須明確分類，不能繼承「入口恰好沒接線」 |
| 復原（undo） | 否 | 否 | 不得影響已完成的計量 |

## 5. 計量契約（[待決]：每一項都必須在實作前定案）

| # | 問題 | 現況 | 候選方案 | 建議（待確認） |
|---|---|---|---|---|
| M1 | 「完成」的定義 | 終局 `won`／`drawn` 存檔 | 維持；是否加入「認輸／放棄」 | 先不新增認輸功能；把「放棄」明確定義為**未完成** |
| M2 | 試玩額度何時扣 | 終局 | (a) 開局預留；(b) 終局（現況）；(c) 達一定步數後 | **(c)**：避免當機即扣，又避免「玩到終局前就離開」無限免費。門檻須由 Owner 定 |
| M3 | 獎勵額度何時扣 | 開局預留 | 維持；放棄時退還 | 與 M2 同一時點，避免兩種額度行為相反 |
| M4 | 同時未完成的對局數 | 未限制（推論 3） | 限 1；限 N | 限 1，新局取代舊局時舊局標記放棄並保留棋譜 |
| M5 | 重新開始 | 新 UUID 再準入 | 視為同一場；視為新場 | 同一場（沿用原準入，不重複扣、也不重複送試玩）；需再定「換規則重開」算不算 |
| M6 | 副本（candidate copy） | 不計量 | 計入原局；視為新場 | 視為原局延續，不產生新的免費額度 |
| M7 | 解鎖者 | 不入帳 | 仍記錄匿名計數 | 維持不入帳（隱私最小化） |
| M8 | 升級與恢復購買 | 恢復後 `isUnlocked` 才為真；額度不重置 | 維持 | 維持：**不重置免費額度，不重複扣同一場** |
| M9 | 帳本損毀 | 已有保護：存局保留，解鎖者不受影響 | 維持 | 維持，並加入 C0 的邊界測試 |

## 6. 存檔與規則識別契約

| # | 要求 | 驗證方式 |
|---|---|---|
| S1 | 每筆對局記錄保存**規則識別**（原版 `RecordRules` 或擴充 `rules` 字串＋`version`），續玩一律依記錄內的規則，不依 App 目前預設 | 用舊記錄＋改過預設的 App 設定續玩，結果規則不變 |
| S2 | 缺少新欄位時採**原版預設**，不報錯、不升級規則 | 欄位刪減的存檔載入測試 |
| S3 | 兩種記錄型別不得互相讀取：原版記錄庫拒絕擴充動作；擴充庫不吞下 1.0 記錄 | 已有單元測試；需補「同一資料夾兩種檔案並存」的整合測試 |
| S4 | 記錄與帳本以**同一識別**對映；擴充記錄須有可對帳的身份 | §3 的缺口；L1 前先定欄位與舊檔缺省值 |
| S5 | 升級後 1.0 出貨二進位寫出的真實存檔可被整合版讀取並續玩 | **需要由 1.0 出貨版產生的真實存檔樣本**（目前沒有；單元測試不能取代） |
| S6 | 存檔位元組上限與損毀處理沿用現有行為（`byteLimit`、原檔保留） | 沿用既有測試 |

## 7. 入口一致性規格（對應審查「一個呼叫點不等於所有入口受控」）

**機制建議：** 所有「建立完整對局」的路徑必須經過同一個準入函式（例如 `MatchAdmission.begin(kind:rules:id:)`），UI 的 `canStartMatch` 只負責顯示，不是權限本身。

**入口列舉測試（必須全部通過才算 C0 關閉）：**

| 測試 | 內容 |
|---|---|
| E1 | 以反射或靜態掃描列出所有會建立 `MatchRecord`／`ExpansionMatchRecord` 的函式；每個都必須呼叫準入，或在**白名單**（教學、挑戰、練習、重播、續玩）內並附理由 |
| E2 | 白名單入口不得寫入帳本，也不得因為名稱叫 Solo／Expansion 而進白名單 |
| E3 | 準入失敗時不留下半成品記錄（沿用 `newMatch` 的「先存記錄、授權失敗則刪除」）；失敗路徑對每個入口各測一次 |
| E4 | 同一 UUID 重複準入、重複完成、不同 `kind` 重用 UUID 的行為與現有帳本一致 |

## 8. 行為驗收矩陣（先寫期望，再實作；期望取自 §5 定案值，目前以建議值填寫）

| 情境 | 期望 |
|---|---|
| 新安裝，開原版完整對局並打到終局 | 試玩剩餘 3 → 2 |
| 新安裝，開局後離開不打完 | 依 M2；建議：未達門檻不扣 |
| 試玩 3 場完成後再開新局 | 要求獎勵或購買 |
| 觀看獎勵後開局 | 消耗 1 個獎勵額度；同一 requestID 不能再被使用 |
| 中途「重新開始」 | 依 M5：不產生第二個免費額度 |
| 使用牧師完成一場 | 與原版共用同一額度；不另開帳本 |
| 擴充對局完成後重開 App | 帳本與記錄對帳一致，不重複扣、不漏扣 |
| 解鎖後 | 所有完整對局不入帳；撤銷後已準入的未完成局仍可續玩 |
| 舊存局（1.0 產生）續玩並完成 | 規則不變；不追溯計量（依帳本現行行為） |
| 帳本檔損毀 | 解鎖者與既有存局不受影響；顯示可理解的錯誤 |

## 9. 不在 C0 範圍

購買畫面與文案、廣告 SDK 行為、價格與地區、App 隱私申報、介面版面、動畫與語音。C0 只決定**語意與測試規格**。

## 10. C0 的關閉條件

1. Owner 對 §4 分類與 §5 M1–M9 逐項回覆（可標「照建議」）。
2. §3 的記錄身份缺口有明確解法（S4）。
3. 入口列舉測試（E1–E4）的規格被接受；允許先寫成「預期失敗」的測試骨架。
4. S5 的真實存檔樣本取得方式確定（或明確標為已知缺口）。

關閉後才進入 L1（規則／存檔／內容／Bot 嫁接）。
